1. PROJECT OVERVIEW (quick recap)
==================================================================

We're building an interactive map of the UT campus that gives directions
between any two points while taking traffic into account. The backend is
all C++: the road network is a weighted directed graph stored as adjacency
lists, where intersections are nodes and road segments are edges. Each edge
has a length, capacity, free-flow travel time, and current congestion. Each
node also stores a list of buildings located there. Routing uses Dijkstra's
algorithm, and the user can tell it to avoid certain roads. The program
outputs the route, congestion along it, and estimated travel time.

The website is just a simple frontend (campus map, roads colored by
congestion, pick a start/end). It is NOT where the bulk of the work is.

How we split it up (subject to change):
  - Eric: getting the real map data and turning it into our graph,
    the graph data structure itself, and the traffic/congestion simulation.
  - Abraham: Dijkstra + routing, road closures / avoided roads, turn by
    turn direction output, and hooking the backend up to the website.

Feedback from Dr. Emrich:
  - Getting the seed data is not trivial, so I need to actually research
    the options and not assume it'll be easy. That's why data acquisition
    is a big chunk of my rubric below.
  - Since we're already implementing Dijkstra's for the next class project,

2. DATA SOURCE RESEARCH (what I found so far)
==================================================================

Options I looked at for getting the campus road network:

  a) OpenStreetMap (OSM) through the Overpass API
     - Free. Roads are "ways" tagged with key=highway, and you can query
       everything inside a lat/lon bounding box (south, west, north, east).
     - You can test queries in overpass-turbo before writing any code.
     - Gives node coordinates, which lets me compute edge lengths, and
       tags like oneway, which matters since our graph is directed.
     - Data is licensed under the ODbL, so we have to credit OpenStreetMap
       on the map (https://www.openstreetmap.org/copyright).
     - Downside: no traffic data at all, and no capacity numbers, so I'll
       have to estimate capacity from road type (e.g. primary vs.
       residential vs. service road).

  b) Google Maps Platform (Routes API etc.)
     - Has real traffic-aware travel times, which is cool.
     - But it costs money past the free tier, needs an API key, and
       Google's terms limit how long you can cache/store their content,
       so building our whole graph out of it seems like a bad idea.
     - Might still be useful as a sanity check (compare our estimated
       travel times against Google's for a few routes).

  c) Hand-entering roads from the UT campus map
     - Most control but super tedious and error prone. Backup plan only.

Current plan: use OSM for the road network, simulate traffic ourselves,
and maybe use Google for a handful of comparison routes if it's not a pain.

Task: Graph data structure + edge list loader (Milestone 1, task 1.2)

  Files:   src/graph.h, src/graph.cpp, src/graph_test.cpp, Makefile,
           data/test_small.txt
  Commit:  https://github.com/e-mcilrath/cs303-final-project/commit/bd073ba38cc7d676ec224e1c81319947363a9d85
  Branch:  main

  How to build/run:
    make
    ./bin/graph_test data/test_small.txt

  What it does:
    Node, Edge, and Graph classes. Each Node has an id, lat/lon, a list of
    buildings, and its outgoing edges (adjacency list). Each Edge has the
    destination, length, capacity, free flow time, current volume, and
    road name, and congestion() gives volume / capacity. Graph::read()
    loads our text format (NODE / EDGE / BUILDING lines) and stops with
    the line number if something in the file is bad (unknown node,
    duplicate id, non-number, length <= 0, etc). graph_test loads a small
    hand-made 6 node test graph (with a one way road) and prints each node
    with its edges.

    Node ids are long long because OSM ids are too big for an int, and the
    graph keeps a map from id to index so the OSM converter in milestone 2
    can use the real ids directly.
